## 二、P0：仍是资金 / 资损面

### ✅ P0-1 优惠券"使用"没有 CAS，可并发重复核销 —— 已修复 2026-10-14
- **证据**：`byw-promotion/.../CouponServiceImpl.java:157-172` —— 先 `selectOne(status=0)` 再 `updateById(status=1)`，两步之间没有任何原子性。
- **影响**：并发请求或重放同一张券时两次都能成功 → **重复折扣**（与订单状态未加 CAS 之前是同一类缺陷）。
- **修复**：改为条件更新 `UPDATE ... SET status=1, used_time=? WHERE coupon_id=? AND user_id=? AND status=0`，
  按影响行数判定：0 行即失败（再查一次仅用于区分"已使用/未持有"的文案）。优惠金额改为**核销成功后**计算，
  门槛不足等异常会让整个事务回滚，券状态不会残留为已使用。

### ✅ P0-2 用券时不校验有效期与状态 —— 已修复 2026-10-14
- **证据**：`CouponServiceImpl.java:151-167` 只判断 `coupon != null`；有效期仅在**领取**时校验（`:94-97`），`status==1` 未校验。
- **影响**：**过期券、已下线的券依然可以抵扣**。前端不下发不等于服务端安全，直接调接口即可绕过。
- **修复**：`useCoupon` 内补 `status==1` 与 `now ∈ [startTime, endTime]`（起止时间做了空值保护）。
  同时给 `calculateDiscount` 加了兜底：`min_amount` 为空按 0 处理（原先会 NPE）、
  `type/discountValue` 缺失直接报"配置异常"、折扣比例被配成 >1 时把优惠额夹在 `[0, 订单金额]`，
  避免"优惠"变成反向加价。

### ✅ P0-3 `t_coupon_record` 缺 `(coupon_id, user_id)` 唯一键 —— 已修复 2026-10-14
- **证据**：`docs/database/byw_promotion.sql:24-34` 只有 `idx_user_id`/`idx_coupon_id` 两个普通索引；`CouponServiceImpl.java:124-138` 是"先查再插"。
- **影响**：并发的重复领取会写入两条记录（同一张券拿到两份），Redis 计数只是前置闸门、挡不住并发。
- **修复**：全量脚本加 `UNIQUE KEY uk_coupon_user (coupon_id, user_id)`；`claimCoupon` 捕获 `DuplicateKeyException`
  → 归还 Redis 计数并抛出"已领取过该优惠券"；增量脚本见
  `docs/database/migration/2026-10-14_coupon-user-unique-and-aftersale-active-unique.sql`（含重复数据预览与消解、通用回滚）。

### ✅ P0-4 售后申请无唯一约束，"重复提交"会生成两张售后单 —— 已修复 2026-10-14
- **证据**：`byw-order/.../AfterSaleServiceImpl.java:80-121` —— `selectCount(进行中)` 之后直接 `insert`；`docs/database/byw_order.sql:76-105` 中 `t_after_sale` 只有 `after_sale_no` 唯一。
- **影响**：双击"申请退款"即可产生两条售后单；**两条单的 `afterSaleNo` 不同，所以按 `refNo` 的退款幂等挡不住它们**。目前唯一兜底是支付侧的"累计退款 ≤ 支付金额"。
- **修复**：MySQL 没有部分唯一索引，改用虚拟生成列 + 唯一键：
  `active_flag = CASE WHEN deleted = 0 AND status IN (0,1,5,6) THEN 1 ELSE NULL END`，
  `UNIQUE KEY uk_item_active (order_item_id, active_flag)`（唯一索引不约束 NULL，所以终态与逻辑删除的行仍可多条）；
  `apply` 捕获 `DuplicateKeyException` 并返回同一句业务提示。

### ✅ P0-5 领券计数未与数据库对齐、且无 TTL —— 已修复 2026-10-14
- **证据**：`redisUtil.increment(COUPON_CLAIM_KEY + couponId)`（`CouponServiceImpl.java:116`）从 0 起算，**从不按 DB 的 `claimed_count` 初始化**；Redis 重启即归零。DB 侧另有一套 `claimed_count` 自增（`:141-142`），两者永久漂移且无对账。
- **影响**：Redis 重启/清空后可**超发**；`listAvailable` 的 `claimed_count < total_count` 判断与实际领取量不一致。
- **修复**：**删掉 Redis 计数**，额度改为数据库原子占用
  `UPDATE t_coupon SET claimed_count = IFNULL(claimed_count,0)+1 WHERE id=? AND IFNULL(claimed_count,0) < total_count`，
  0 行即"已领完"。自增与领券记录处于同一事务，任何一步失败一起回滚 —— 既不会超发也不会漂移，
  也不再需要"归还计数"这类手工补偿。列表查询的额度判断同步改为 `IFNULL` 版本（原先 `claimed_count` 为 NULL 的券
  能被领却不显示）。
- **权衡**：额度自增会锁住该券所在的行，同一张热门券的领券请求因此串行化（MySQL 行锁，吞吐仍是每秒数千级）。
  若将来领券中心成为热点，再引入 Redis 削峰时**必须同时做基线初始化与对账**，而不是像原先那样把 Redis 当唯一闸门。

### ✅ P0-6 用券失败被静默忽略（做 P0-2 时发现）—— 已修复 2026-10-14
- **证据**：`OrderServiceImpl.createOrder` 原先在 `useCoupon` 返回失败 `R` 时**只跳过优惠、不报错**；
  而 `BusinessException` 的全局处理是 **HTTP 200 + 失败体**（`GlobalExceptionHandler.java:28-34`），不会抛异常。
- **影响**：用户选了券，券过期/已用/已下线/未达门槛 → **订单照常提交并按原价扣款，界面上没有任何提示**。
  P0-2 扩大了这条路径（原先过期券会"成功"抵扣，修复后会走到这里）。
- **修复**：区分两类失败——
  - **业务失败**（券服务明确判定未核销）：**拒绝下单**，把券服务的原始原因返回给前端；
  - **服务不可用**（`getCouponById` 查不到详情 / 调用异常）：保持原有的降级行为（继续下单、不打折），
    避免促销服务抖动导致全站无法下单。
  另外补了一个边角：核销成功但未返回优惠金额时不再按"0 优惠"继续，而是抛错回滚，
  由已登记的补偿把券退回。

## 三、P1：一致性、限流与"有壳没肉"的功能

### ✅ P1-1 ES 同步"静默漂移" + reindex 无权限 —— 已修复 2026-10-14
- **证据**：`byw-product/.../ProductEsService.java:142-159` —— upsert/remove 失败只 `log.warn`；启动时仅在**索引为空**才全量重建（`:58-69`）；`byw-product/.../ProductEsController.java:22-26` 的 `/product/es/reindex` 是唯一修复手段，**却没有任何 `@RequireAdmin`**（注释写着"供管理端/运维手动对齐"）。
- **影响**：商品改名/改价时若 ES 短暂不可用 → 搜索结果**永久过期**，没有任何自动修复；同时任意登录用户都能触发全量重建（扫全表 + 批量写 ES）。
- **修复**：
  1. `/product/es/reindex` 加 `@RequireAdmin`（原先任意登录用户都能触发全表扫描 + 批量写 ES）；
  2. 引入**待补同步集合**（Redis `byw:es:dirty:product`）：`upsert`/`remove` 先登记再尝试写入，
     成功才移除；30 秒的定时探测在 ES 可用时调用 `drainPendingSync()` 逐批补同步
     （以数据库当前状态为准：查得到就 upsert、已逻辑删除就从索引删除），多实例用分布式锁保证单节点执行。
     这样"ES 不可用期间产生的写入"和"单次写入失败"都能**自动收敛**，不再需要人工全量重建。

### ✅ P1-4 网关限流：全局兜底 + 敏感接口精细限流（2026-10-20 收官）
- **证据**：`byw-gateway` 中 `RequestRateLimiter` **0 处**；`@SentinelResource` 全仓仅 11 处，且流控/降级规则来自 Nacos（仓库内无规则文件）。
- **影响**：若 Nacos 未配置规则，全站实际只有两道应用级限制（登录失败锁定、短信 60s 冷却）。短信、文件上传、秒杀、领券是重点风险面。
- **修复（部分）**：网关加**全局兜底限流**：`default-filters` 挂 `RequestRateLimiter`
  （每个 IP 稳态 50 req/s、突发 100，令牌存 Redis —— 网关本就依赖 Redis 存 Sa-Token 会话），
  KeyResolver 见 `RateLimiterConfig`，默认**不信任** `X-Forwarded-For`（直连部署下该头可伪造，
  用它当限流键等于没限流），仅在可信代理后面才把 `byw.gateway.rate-limit.trust-forwarded-for` 设为 true。
- **2026-10-20 补齐"按接口"这一层**（原先只有"每 IP 一个全局桶"，存在邻居攻击与敏感接口过宽）：

| 层 | 路径 | key | 稳态/突发 |
|---|---|---|---|
| 路由级 | `/api/auth/login`、`/merchant/login`、`/admin/login`、`/api/admin/auth/login` | IP + 路由 | **5 / 10** |
| 路由级 | `/api/auth/sms/send` | IP + 路由 | **1 / 3**（短信有真实成本） |
| 路由级 | `POST /api/order` | IP + 路由 | **10 / 20** |
| 路由级 | `/api/pay/**` | IP + 路由 | **10 / 20** |
| 全局兜底 | 其余 `/api/**` | IP + 路由 | 50 / 100 |

  - key 从"IP"改成 **"IP + 路由 id"**（`RateLimiterConfig`）：同一 IP 下不同接口**互不占用额度**，
    刷一个读接口不会把同出口（公司/校园 NAT、4G 共享）的正常用户一起限死；
  - 路由级限流是**新增路由**（与通用路由同 `uri`/`StripPrefix`，只多挂一个更严的桶），
    必须放在通用路由之前，先匹配先生效。

- **踩坑（已修，值得记住）**：第一版让全局桶与路由级桶用**同一个 key**（`ip:routeId`），
  结果同一个请求被 `default-filters` 和路由级过滤器**各扣一次令牌**，等效强度翻倍 ——
  实测"登录 12 并发全 429、短信 6 并发全 429"。改为两个后缀（`:global` / `:strict`）后数值立刻正确。
  另外 Spring Cloud Gateway 的 `KeyResolver` bean **必须唯一**，多一个会导致网关启动失败
  （`required a single bean, but 2 were found`），用 `@Primary` 指定默认的那个。

- **真机验证**（网关 8080，清空旧桶后）：

| 用例 | 期望 | 实测 |
|---|---|---|
| 登录路由 ×12 并发 | 10 过 / 2 × 429 | **10 / 2** ✅ |
| 登录桶打满时调 `/api/user/me`、`/api/user/5` | 不受影响，全 200 | **200,200,200** ✅ |
| 短信路由 ×6 并发（1/s、burst 3） | 3 过 / 3 × 429 | **3 / 3** ✅ |
| 等 3 秒后再登录 | 200（令牌已补充） | **200** ✅ |

- **配套**：前端 `shared/http-client.ts` 把 429 映射为中文"操作过于频繁，请稍后再试"
  （`RequestRateLimiter` 返回的 429 **没有响应体**，不处理的话前端只能看到英文错误）。
- **调整/回滚**：参数都在 Nacos 的 `byw-gateway.yml`（`docs/deploy/nacos/services/byw-gateway.yml` + `publish.ps1`）；
  不想用精细限流就删掉那 4 条 `byw-rl-*` 路由；完全不限流则再删掉 `default-filters` 段。

### ✅ P1-5 分页没有上限，`PageQuery` 定义了却无人使用 —— 已修复 2026-10-14
- **证据**：`new Page<>(pageNum, pageSize)` **27 处**，`pageSize` 全部直接来自客户端；带 `@Min/@Max(100)` 的 `PageQuery` 全仓只有 **1 处命中（它自己的定义）**：`byw-common/.../base/PageQuery.java:10`。
- **影响**：一个请求即可拉取海量数据，造成 DB/内存/带宽压力。
- **补充查证（比原判断更严重）**：反编译 `PaginationInnerInterceptor` 确认 —— MyBatis-Plus 对
  `pageSize < 0` **会直接跳过分页**，生成的 SQL 不带 LIMIT，等于把**整张表**返回，而不是"取太多"。
  `setMaxLimit` 只能挡住"过大"，挡不住负数。
- **修复**（在`byw-common-mybatis` 的 `MyBatisPlusConfig` 里统一处理，**不需要改 27 个调用点**）：
  1. 新增 `PageParamNormalizer`（`InnerInterceptor`，排在分页插件**之前**）：`pageNum < 1 → 1`、
     `pageSize < 1 → 10`、`pageSize > 100 → 100`；
  2. 分页插件 `setMaxLimit(100)` 作为第二道兜底。
  这样任何接口都不必自己记得校验分页参数；`PageQuery` 保留不动（它是可选的分页参数载体，不属于漏洞）。

### ✅ Feign 4xx → BusinessException（2026-10-16 已实现并真机验证）

新增 `ErrorDecoder`（`byw-common-security` 的 `FeignRelayAutoConfiguration`）：

- **4xx**：把响应体（统一 `R{code,message}`）还原成 `BusinessException(code, message)`，
  BFF 的全局异常处理器按既有约定输出 —— **401/403 仍是真实 HTTP 状态**，其余业务码为 HTTP 200 + 业务码与中文提示；
- **5xx**：保持 Feign 默认行为（不把服务端故障伪装成业务错误）；
- 响应体不是 `R` 结构时回退到默认解码。

## 六、运行时验证发现并修复的问题（2026-10-16）

本机中间件启起来之后做的真机验证（网关 + BFF + 服务），发现了三个**静态审查看不到**的问题：

### ✅ V0 JetCache 要 FASTJSON2，但依赖没声明 → 三个服务起不来（已修）

启动 byw-user / byw-product / byw-shop 直接失败：
```
com.alicp.jetcache.CacheConfigException: not supported:FASTJSON2
```
两个独立原因：
1. 这三个服务的 `bootstrap.yml` 显式写了 `keyConvertor/valueEncoder/valueDecoder: FASTJSON2`，
   但全仓**从未声明 `com.alibaba.fastjson2:fastjson2` 依赖**；
2. **光加依赖还不够**：反编译确认 JetCache 2.7.9 的 `DefaultEncoderParser` 只内置
   `JAVA/KRYO/KRYO5`（**没有** FASTJSON2），只有 `keyConvertor` 原生支持 `FASTJSON2`；
   valueEncoder 必须走 `DefaultSpringEncoderParser` 的 `bean:<beanName>` 语法引用 Spring bean。

**修复**：三个模块声明 `fastjson2`；`byw-common-redis` 新增
`JetCacheEncoderAutoConfiguration` 把 JetCache 自带的 fastjson2 编解码器注册成 bean，配置改为
`valueEncoder: bean:fastjson2ValueEncoder`。该配置类**刻意用 `@ConditionalOnClass(name=...)` + 反射**
取单例，不在 byw-common-redis 上声明编译期 jetcache 依赖 —— 否则所有服务都会被动引入一个用不到的库，
且 IDE 未重新导入时会直接报"程序包 com.alicp.jetcache.support 不存在"。

**真机验证**：三个服务均可启动；调用 `GET /api/user/5` 后 Redis 出现 `byw:cache:user:info:5`（TTL 1800s），
第二次调用命中缓存并正确反序列化 —— 编码器与解码器都真实生效。

### ✅ V1 审计切面用 `syncSend`，把业务请求拖成 500（开发中新引入，已修）

给 `@OperationLog` 加落库时最初在切面里用 `template.syncSend(...)`。broker 抖动时同步发送
阻塞到生产者超时（3s），把调用方 BFF 的 Feign 读超时（5s）打爆 —— 一次优惠券创建直接返回
**500「系统内部错误」**，而业务本身是成功的。
**修复**：改 `asyncSend` + `SendCallback`，失败只 warn。**副作用绝不能占用业务请求的关键路径。**

### ✅ V2 `shopId=0` 污染会话，平台管理员操作平台级资源被误判越权（P2-7 激活的潜伏 bug）

现象：管理员删除**平台券**（`shop_id` 为 null）返回"无权操作其他店铺的优惠券"。
根因链：
```
AuthServiceImpl.refreshToken 用 session.getLong(SESSION_SHOP_ID)
   → Sa-Token 的 getLong 是原始类型，键不存在时返回 0（不是 null）
   → writeAuthSession 把 shopId=0 写回会话
   → 网关注入 X-Shop-Id: 0
   → 服务端 canAccessShop(null) 走 "0 != null" 分支 → 拒绝
```
该 bug 只在 `/auth/refresh` 被调用后出现，而 P2-7（前端续期）之前没人调过这个接口，所以一直潜伏。
**修复四处**：`refreshToken` 改用 `session.get()` 自行判空；`writeAuthSession` 在 shopId 为空时
**显式 delete** 该键（清掉历史遗留的 0）；网关对 `shopId <= 0` 不再注入 `X-Shop-Id`；
`canAccessShop` 把 `<= 0` 视为"无店铺上下文"，并用 `Boolean.TRUE.equals` 避免 `isAdmin()` 为 null 时拆箱 NPE。
**真机验证**：刷新后会话已无 `shopId`；创建+删除平台券均 **200**。

### ✅ V3 环境问题：RocketMQ broker 通告了不可达 IP（非代码，已修）

### ✅ V4 支付回调原本 fail-open：公开接口无验签即可把订单置为已支付（2026-10-19 已修）

`POST /pay/callback/{channel}` 标了 `@Public`，而两个渠道策略的 `queryStatus()` **恒返回"已支付"**。
早期只靠 `mock-enabled=true` 时的"归属用户"校验兜底 —— 一旦按生产要求关掉模拟开关，这个公开接口就完全敞开：
任何人拿一个 payNo 调一次就能白拿商品。
**修复**：真实回调强制 `hex(HMAC-SHA256(secret, payNo|tradeNo|timestamp))` 验签 + 时间戳窗口防重放，
密钥未配置时**一律拒绝**（fail-closed）；模拟回调拆成 `POST /pay/mock/callback/{channel}`
（`@RequireLogin` + 支付单归属校验 + 开关关闭时 403）。前端改调模拟接口。
**真机验证**：无签名/错签名/过期时间戳 → 401；正确签名 → 通过验签进入业务（返回"支付单不存在"）；
未登录调模拟回调 → 401；非归属用户 → 403 且支付单状态未变；开关关闭 → 403"模拟支付回调未开启"。

### ✅ P2-8(a) 三端 request 层去重（2026-10-20 完成）

- 新增 `byw-frontend/shared/http-client.ts`（**零依赖 + 依赖注入**）：token 续期/单飞刷新、

- 每端新增 `src/utils/token.ts`，token 键名只在一处定义（原来散在 store/router/上传组件/IM socket 共 14 处）；
- `vite.config.ts` 增加 `server.fs.allow: ['..']` 允许 dev server 读取共享目录；

### ✅ P2-8(b) 后端"双模式"认证（2026-10-20 完成并验证）

先让 **gateway + auth 同时接受 `Authorization: Bearer` 和 HttpOnly Cookie**，前端暂不改 —— 
任一步出问题都能单独回退，不用三端一起动。

| 改动 | 内容 |
|---|---|

| 4 | **只带 Cookie** 调 `/auth/refresh` | 200 + **新 Set-Cookie** ✅（轮换正确） |

| 6 | 完全不带 token | **401** ✅ |

### ✅ P2-8(c) 前端切到 Cookie（2026-10-20 完成，构建通过）

admin / merchant 两个 SPA 已切换为 Cookie 模式（Nuxt 端 byw-web 保持头模式，后端双模式兼容）：

| 文件 | 改动 |
|---|---|
| `shared/http-client.ts` | 新增 `cookieMode`：`withCredentials: true`、不注入 `Authorization`；`/auth/refresh` 与 `/auth/token-ttl` 也走 Cookie（服务端用 `Set-Cookie` 轮换） |
| 两端 `utils/token.ts` | 从"存 token"改成"存登录标记"（`admin_logged_in` / `merchant_logged_in`），登录/登出顺带清理历史 `*_token` |
| 两端 `utils/request.ts` | `cookieMode: true` + `clientApp: 'admin' / 'merchant'`（请求带 `X-Client-App` 头）；401 时 `clearToken()` + 跳登录 |
| 两端 `stores/user.ts` | 不再把 token 放进内存 ref；**登出改为真正调用 `/auth/logout`**（原先只清本地，Cookie 模式下会导致"登出后刷新又登上了"） |
| 两端 `ImageUpload.vue` | `:headers` 改为 `:with-credentials="true"`（上传不再依赖 token 头） |
| `merchant/utils/imSocket.ts` | WS 地址去掉 `?token=`，改由浏览器自动带 Cookie |
| `byw-im/ws/ImHandshakeInterceptor` | 握手 token 解析支持 **Cookie 兜底**（query 参数仍兼容），否则切 Cookie 后 IM 连不上 |
| **三端 Cookie 隔离**（2026-10-21 修） | 三个前端通常同 host（本地都是 localhost，仅端口不同），而 **Cookie 不区分端口**：原先三端共用一个 `byw_token`，后登录的端会覆盖前面的 → 管理端拿着 C 端身份调接口 → **403**。现按端命名：`byw_token_admin` / `byw_token_merchant` / `byw_token`(C 端)；网关与 auth 按 `X-Client-App` 头 + 路径前缀选 Cookie；IM 握手按"商家 → C 端 → 管理端"顺序尝试 |

**三端隔离验证（真机）**：管理端 Cookie → 管理端接口 200、C 端 Cookie → 管理端接口 **401**；
C 端 Cookie → C 端接口 200、管理端 Cookie → C 端接口 **401**；**两端 Cookie 并存时各自接口都是 200**（互不干扰）；
`refresh` 带 `X-Client-App: admin` 只轮换 `byw_token_admin`。

验证：`mvn -pl byw-im -am compile` ✅；两个 SPA `npm run build` ✅；SPA 内已无 `Bearer`/`?token=`/`*_token` 字面量残留。
**回退**：把 `request.ts` 的 `cookieMode` 改回 `false` 即可回到头模式（后端两种都接受）。

**⏭ 浏览器侧验证清单**（需人工点一遍）：

1. `http-client.ts` 加 `withCredentials: true`，去掉 `Authorization` 注入；
2. 各端 `token.ts` 不再读写 token，登录态改为"调 `/user/me` 探测"或读一个非敏感的登录标记；
3. 登录/登出不再手动存删 token；
4. 生产要求：前端域名与网关同站（或 CORS 明确 origin + allowCredentials，网关已支持）；
5. 切换后必须回归：登录 → 刷新 → 401 跳登录 → 登出。

> 为什么不一口气切：Cookie 的 `Domain/SameSite/Secure` 在 dev（vite proxy、http、跨端口）与生产（域名、https）
> 行为不同，浏览器侧不易自动化验证；后端双模式已验证，前端切换失败可立刻回退到"头"模式。

### ✅ V7 改共享模块后 jar 没重打包，新依赖静默缺失（2026-10-20 落地 Jasypt 时踩到）

给 `byw-common-core` 加 jasypt 依赖后跑了 `mvn -DskipTests package`（BUILD SUCCESS），但
**byw-auth / byw-gateway 的 fat jar 时间戳还是前一天的** —— Maven 认为这两个模块的 `target/classes`
没变化，跳过了 jar 重打包，于是旧 jar 里没有 jasypt。

后果非常隐蔽：服务能启动，但共享配置里的 `byw.security.internal-secret: ENC(...)` **没被解密**，
byw-auth 拿着字符串 `ENC(...)` 去签服务间请求，被 byw-user 的 `@InternalApi` 验签拒绝 →
**登录接口返回 403「无权限访问」**。

**教训/规定**（2026-10-20 又踩到两个变种，一并记下）：

1. 改共享模块后必须 `mvn -DskipTests clean package`（或 `-pl <服务> -am package`），不能只 `package`；
2. **`-pl <服务>` 不带 `-am` 会从本地仓库取 SNAPSHOT** —— 本地仓库若没 `install` 过最新共享模块，
   就会用旧版本（实测 byw-im 因此拿到 10/16 的 byw-common-core，**jar 里没有 jasypt**，
   表现为数据源密码没解密 → `Access denied`，同时内部签名密钥也是 `ENC(...)` 原文 → 网关调用 401）；
3. **`mvn install` 不会重打已构建的 fat jar** —— 更新本地仓库后仍需对受影响服务 `clean package`；
4. 验证手段：`jar tf <服务>.jar | Select-String jasypt`、`jar` 时间戳、或看日志里有没有
   `Access denied` / `身份头签名校验失败`。
